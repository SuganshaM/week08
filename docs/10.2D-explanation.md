# 10.2D: Infrastructure, Security and Monitoring in the Pipeline

## Explanation (for submission)

Terraform, Docker Scout, and Prometheus/Grafana were added as three
independent stages that sit alongside, rather than inside, the existing
CI/CD chain. **00 - Terraform** runs in parallel with **01 - CI** on every
push, running `fmt`/`validate`/`plan` for visibility on every change and
`apply` once changes land on `main`; it manages a new Log Analytics
workspace and an AKS Container Insights add-on, using a remote Azure
Storage backend so the pipeline shares state with local runs instead of
re-discovering already-provisioned infrastructure. **Docker Scout** was
placed inside **01 - CI**, after each image is built but before it is
pushed to ACR, so a vulnerable image is scanned while it only exists on
the runner, not after it has reached the registry or a deployable
namespace. It runs with `continue-on-error`, since the task calls for
reviewing and remediating findings, not gating every build on CVE counts.
One remediation was applied directly: all five Python service Dockerfiles
now run `apt-get upgrade` for the base image's OS packages, which Scout
had flagged as carrying outdated Debian packages. **Prometheus and
Grafana** (via the `kube-prometheus-stack` Helm chart) were deployed as a
new **05 - Deploy Monitoring** workflow, triggered after staging deploys
successfully, but deliberately not gating the staging-test or
production-promotion workflows - the app's own tested/promoted state
should never depend on whether the monitoring stack is healthy.
`user-service` was instrumented with `prometheus-fastapi-instrumentator`
and a `ServiceMonitor` per namespace, giving Prometheus both
Kubernetes-level metrics (pod CPU/memory/restarts via
`kube-state-metrics`/cAdvisor) and application-level metrics (HTTP
request rate/latency), visualised on a single Grafana dashboard covering
staging and production side by side. Together these three stages turn
the pipeline from "build, test, deploy" into a DevSecOps workflow that
also provisions its own supporting infrastructure, screens images before
they ship, and gives visibility into what's actually running.

*(~300 words)*

## New GitHub Actions repository variables/secrets required

These are **in addition to** what your Week08 pipeline already uses.

| Name | Type | Purpose |
|---|---|---|
| `TF_STATE_STORAGE_ACCOUNT` | Variable | Storage account (from `terraform/storage_account.tf`) used to hold the remote Terraform state (`tfstate` container) |
| `AKS_DNS_PREFIX` | Variable | Passed to `terraform plan`/`apply` as `-var="aks_dns_prefix=..."` |
| `GRAFANA_ADMIN_PASSWORD` | Secret | Sets the Grafana admin password on install |

Your existing `AZURE_CREDENTIALS` secret and `ACR_NAME` / `ACR_LOGIN_SERVER`
/ `AKS_RESOURCE_GROUP` / `AKS_CLUSTER_NAME` variables are reused as-is.

## One-time manual steps before the first pipeline run

1. **Migrate local Terraform state to the remote backend**, so the
   pipeline's `terraform plan` reflects your already-provisioned
   infrastructure instead of trying to recreate it:
   ```bash
   cd terraform
   terraform init -migrate-state \
     -backend-config="resource_group_name=<your-rg>" \
     -backend-config="storage_account_name=<your-storage-account>" \
     -backend-config="container_name=tfstate" \
     -backend-config="key=week08.tfstate"
   ```
2. Ensure the Service Principal behind `AZURE_CREDENTIALS` has
   `Storage Blob Data Contributor` on the storage account (for state) and
   `Monitoring Contributor`/`Log Analytics Contributor` (for the new
   diagnostic settings).
3. After `05 - Deploy Monitoring` runs, get the Grafana URL:
   `kubectl get svc monitoring-grafana -n monitoring` and log in as
   `admin` with `GRAFANA_ADMIN_PASSWORD`.
